# Bey Lab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An offline iPad home-screen web app that logs Beyblade X test battles, computes risk-weighted matchup stats, finds the best legal 3on3 deck, and suggests what to test next.

**Architecture:**
- The app is a static site with no build step, written in plain ES modules.
- The logic modules are pure and DOM-free: scoring, stats, catalog, combos, matchups, sim, lineup and suggestions. They run in both Node (for tests) and the browser.
- A thin UI layer renders five tabs. Persistence is IndexedDB behind a small backend interface, with an in-memory backend for tests.
- Lineup computation runs in a Web Worker. A service worker caches the app shell and the hotlinked reference photos.

**Tech Stack:**
- HTML, CSS and vanilla JS (ES2022 modules), with no runtime dependencies.
- Tests use Node 26's built-in runner (`node --test`).
- Data is stored in IndexedDB.
- Hosted on GitHub Pages via a GitHub Actions deploy of `app/`.

**Spec:** `docs/2026-11-06-bey-lab-design.md`. Read it fully before starting any task. The parts catalog is `docs/parts-catalog.json`, and Task 1 moves it to `app/data/parts-catalog.json`.

## Global Constraints

- **Full names everywhere in the UI.** Write "Pegasus Blast 2-60 Free Ball", never "Blast" or "PB". Every part shows the user's preferred name, falling back to the catalog name.
- **Scoring:** Spin = 1, Burst (B) = 2, Pocket (P) = 2, Xtreme = 3. A draw scores 0 for both sides. An untyped result stores `finish: 'unknown'` with explicit points.
- **Format:** 3on3. Matches are first to 5, and first to 7 from the semi-finals on. Battle *i* of a set is our slot *i* vs their slot *i*. The opponent's order is uniformly random each set. Points may overshoot the target, and the match ends right after the battle that reaches it.
- **Deck legality:** no physical part twice in a deck. That covers blade, ratchet, bit, ratchet-integrated bit, lock chip, main blade, over blade, metal blade and assist blade.
  - Built-in-ratchet blades and ratchet-integrated bits have `ratchet: null`.
- **Statistics:**
  - Wilson interval, z = 1.96, for P(win) and P(lose).
  - t interval for EV, with df = n−1, using a two-sided 95% t table.
  - Bayesian P(EV<0) from a Dirichlet over outcomes `[-3,-2,-1,0,1,2,3]`, with prior 1/7 per outcome and 20,000 draws.
- **Never show EV or a ranking without its uncertainty.** A pairing with no data reads "unknown", never "even".
- **Flag thresholds** (Claude's call):
  - `burst-risk` when losses by Burst are at least 0.20 of battles.
  - `ko-risk` when losses by Pocket plus Xtreme are at least 0.30 of battles.
  - `low-data` when a pairing has fewer than 10 battles.
- **Simulation sizes:**
  - `SCREEN_MATCHES = 1000`, using the posterior-mean distribution.
  - `REFINE_OUTER = 200` posterior draws × `REFINE_INNER = 50` matches.
  - `TOP_N = 5` decks refined.
  - All randomness goes through `src/rng.js`, which is seeded in tests.
- **Reference photos are hotlinked, never bundled.** Every `<img>` uses `referrerpolicy="no-referrer"`. Service-worker fetches of `static.wikia.nocookie.net` use `{ referrerPolicy: 'no-referrer', mode: 'no-cors' }`.
- **Touch:**
  - Interactive controls are at least 56 px tall.
  - `touch-action: manipulation` on the body, so double-tap doesn't zoom.
  - Target iPadOS Safari 17+, in portrait and landscape.
- **No browser `alert`, `confirm` or `prompt`.** Use in-app dialogs.
- Every write persists immediately, so there's no Save button.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **Logging the same combo on both sides** (left === right) is rejected with a message, because you can't battle a combo against itself. Tested in Task 5 as `addBattle rejects identical combos`.
2. **A bad or old Import file** (wrong `version`, missing arrays, invalid JSON) leaves existing data untouched and shows an error. Tested in Task 5 as `importData rejects bad file without changing state`.
3. **Merging or renaming a user part** (e.g. "Pop Out (unverified)" into a catalog bit) repoints every combo that uses it. Battles and stats stay unchanged, and no duplicate combos are left behind. Tested in Task 5 as `mergePart repoints combos and dedupes`.
4. **Storage unavailable or wiped by Safari** (private mode, IndexedDB open failure). The app shows a persistent "data is NOT being saved" banner instead of failing silently. It calls `navigator.storage.persist()` on start. Tested in Task 5 as `createStore surfaces backend failure`. The banner is checked manually in Task 11.
5. **A huge iPad camera photo** (12 MP or more) is downscaled before storing, so it can't bloat storage or Export. Covered in Task 15 by `downscaleDimensions caps the long edge at 1280`.

### Task 8: 3on3 match simulator

**Files:**
- Create: `app/src/sim.js`
- Test: `app/tests/sim.test.js`

**Interfaces:**
- Consumes: `rng`, `dirichlet` and `shuffle` (Task 2), and probability vectors over `OUTCOMES`.
- Produces:
  - `playMatch(probs, target, rng, lead) → boolean`. It returns whether we win.
    - `probs[i][j]` is the outcome probabilities when our combo *i* faces their combo *j*, each a number[7].
    - `lead` is null or our index 0–2. If it's set, that combo is always our slot 1, and our other two are shuffled each set. If it's null, our whole order is shuffled each set.
    - Their order is shuffled each set.
    - A positive outcome adds to our score, a negative one adds `|x|` to theirs, and 0 adds nothing.
    - The match ends as soon as either score is at least `target`.
  - `matchWinPoint(countsMatrix, target, {rng, matches, lead}) → number` uses posterior-mean probabilities: `(counts + 1/7) / (n + 1)`.
  - `matchWinPosterior(countsMatrix, target, {rng, outer, inner, lead}) → {p, lo, hi}`. For each of `outer` draws, it samples one Dirichlet per cell, plays `inner` matches, and records the win fraction. `p` is the mean, and `lo`/`hi` are the 2.5th and 97.5th percentiles.
  - `countsMatrix[i][j]` is `{counts, n}` from `pairingDistribution`.

- [ ] **Step 1: Write the failing tests.**
  - With every cell `[0,0,0,0,1,0,0]` (always +1), the win rate is 1.0.
  - When every cell is mirrored-symmetric, the win rate is 0.5 ± 0.03 over 20,000 matches.
  - With all 9 cells set to the Red Hulk vs Wizard Rod empirical probabilities, the win rate is within 0.03 of `matchupStats(rhWr).race[5]`. All cells being identical makes it the single-pairing race.

### Task 10: Next-test suggestions

**Files:**
- Create: `app/src/suggest.js`
- Test: `app/tests/suggest.test.js`

**Interfaces:**
- Consumes: lineup outputs (Task 9), matchups and flags (Task 6), Combo helpers (Task 4), merged parts (Task 3).
- Produces: `suggestTests(state, parts, lineupResult) → Suggestion[]`, at most 8.
  - Suggestion: `{kind, left:Combo, right:Combo, battles:10, reason:string}`. `left` and `right` may be new combos not yet in the state.
  - `kind` is one of `'baseline'|'stage1'|'stage2'|'blocking'|'narrow'|'fix'`.
  - The order, which is a spec decision:
    1. `baseline`: missing pairings among core field combos.
    2. `blocking`: missing pairings from `blocked[0..2]`.
    3. `stage1`: candidates missing any core pairing.
    4. `stage2`: candidates whose leaderboard `evCI` overlaps the range of evs of the top-ranked deck's members, missing a non-core active pairing.
    5. `fix`, for flagged combos:
       - `burst-risk` or `ko-risk`: the same blade with another owned bit, then another owned ratchet. The swapped part must not be used by the other two members of the top or first blocked deck.
       - Field illegal: for each clash, a swap that uses owned parts to make the field legal, including ratchet-integrated bits like Turbo.
    6. `narrow`: pairings inside the top deck whose t-interval width is over 1.5 and whose n is under 30.
  - Duplicates are removed by unordered pair.
  - The reason is one line using full names, e.g. `"Pegasus Blast 2-60 Pop Out (unverified) was burst in 5 of 20 battles — test a different bit."`
  - When `left` and `right` share a physical part, append `" (needs two of <part>)"` to the reason.
